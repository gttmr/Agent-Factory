8. Build와 Verify

승인된 산출물이 모이면 BuildWorkbench는 scaffold-plan.json을 만들고 runtime-stub/ source bundle을 생성한다(기본 smoke TODO 번들, 승인된 output_mode: runnable 에서는 실행형 ADK 2.1 Workflow). VerifyWorkbench는 고정된 검증 명령을 실행하고 evidence를 남긴다. 이 단계는 배포가 아니라 review-gated source-bundle handoff다.

BuildWorkbench의 책임

작업의미
scaffold-plan.json 생성승인된 AnalysisResult, module candidate, Runtime 계약, Graph IR, catalog decision만 입력으로 삼는다.
runtime-stub/ 생성scripts/generate-adk-source.mjs를 artifact root 기준으로 실행해 source bundle을 만든다. 기본 smoke는 TODO/runtime wiring 번들, output_mode: runnable 은 LlmAgent + Mock Lab MCP 어댑터 ADK 2.1 Workflow.
implementation-handoff.md후속 구현자가 실제 wiring과 business logic을 채울 때 볼 handoff notes를 inline 편집한다.
stub_ready_for_followupstub directory가 비어 있지 않고 reviewer가 결과를 확인한 뒤에만 토글하는 manifest gate다.
!

raw requirement는 source generation 입력이 아니다. BuildWorkbench는 승인된 scaffold-plan만 넘긴다.

Build gate

  • analysis_reviewed가 true여야 한다.
  • boundaries_approved와 runtime_contracts_approved가 true여야 한다.
  • candidate-level needs_info와 missing_information이 남아 있으면 차단된다.
  • Graph IR validation error가 있거나 approved module이 Graph node로 덮이지 않으면 차단된다.
  • 필수 Runtime 계약의 contract_status가 approved가 아니면 차단된다.

차단되면 BuildWorkbench는 blocker를 보여주고 Design route로 돌아가서 Stage Runner proposal을 적용하거나 사람이 검토를 마치도록 안내한다.

VerifyWorkbench의 책임

VerifyWorkbench는 임의 shell을 실행하지 않는다. 현재 allow-list는 세 명령으로 고정되어 있다.

node scripts/validate-artifacts.mjs <artifact-root>
npm run build --prefix packages/web
npm run test:analyzer --prefix packages/web
  • stdout/stderr와 exit code는 manifest.validation.last_result에 기록된다.
  • validation-report.md는 reviewer가 남기는 검증 요약이다.
  • catalog-delta.yaml은 catalog 등록/수정 제안이다. catalog/*.yaml은 직접 편집하지 않고 Reuse Hub 등록 승인 publish 경로 또는 human PR merge 로만 반영한다.

런타임 실행과 smoke

워크벤치 UI 안에는 여전히 adk web iframe 임베드도, 워크벤치 자체 챗도, Smoke 일괄 실행 macro도 없다. 대신 게이트 없는 실행 화면(/af/:reqId/run)이 runtime-stub/에 대해 adk api_server --with_ui(8765)를 시작/중지하고 ADK 공식 dev UI(채팅·트레이스)를 새 탭으로 링크한다. 코드 레벨 smoke(compileall/pytest)는 생성된 번들에서 직접 돌린다.

Done의 의미

  • raw requirement가 scaffold input으로 쓰이지 않는다.
  • module 분류가 활성 taxonomy를 따른다.
  • category에 맞는 subtype 필드가 존재한다.
  • Remote A2A는 high-friction이고 contract-backed다.
  • Runtime 계약과 manifest approval 상태가 source generation 전에 맞춰져 있다.
  • schema, validator, analyzer types, UI label이 enum 변화에 맞춰 정렬되어 있다.
  • review artifact와 deferred fixture가 검증을 통과한다.
  • private banking 데이터/credential/endpoint/deployment script/organization-specific runtime 코드가 추가되지 않았다.

퀴즈

Q1. 후보 2개가 needs_info인 상태에서 Build route에서 runtime stub 생성을 누르면?

정답: 차단. candidate-level missing은 hard gate다. Design Stage Runner proposal을 적용하거나 사람이 모듈 검토를 끝내야 한다.

Q2. 생성된 stub의 ADK 챗·트레이스 UI를 보고 싶다. 워크벤치는 이걸 어떻게 제공하나?

정답: 실행 화면의 링크. ADK가 --with_ui로 제공하는 완성형 dev UI(채팅·세션·이벤트·트레이스)를 새 탭으로 연다 — 워크벤치 자체 챗이나 iframe 임베드는 만들지 않는다. 코드 레벨 smoke(pytest 등)는 생성된 번들에서 직접 돌린다.

Q3. 검증 중 catalog에 새 reusable adapter를 등록해야 한다는 사실을 발견했다. Verify route는 무엇을 남기나?

정답: catalog-delta. 실제 catalog YAML 반영은 Reuse Hub 등록 승인 publish 경로 또는 별도 reviewer merge 작업이다.
