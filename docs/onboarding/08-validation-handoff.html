8. 검증과 ADK Runtime Handoff

승인된 산출물이 모이면 워크벤치는 scaffold-plan.json을 만들고 ADK source bundle을 핸드오프한다. 이 단계는 “배포”가 아니라 검토 게이트 + source-bundle handoff + smoke 검증이다. 이 장은 검증 규칙, scaffold-plan, smoke 일괄 실행 macro, stub runtime 배너, 검증 명령을 본다.

ADK Runtime Handoff는 무엇이고 무엇이 아닌가

맞는 것아닌 것
승인된 workbench artifact만 입력으로 받는 review-gated source-bundle handoff raw requirement에서 자동 코드 생성
generated source의 구조 검증 (compileall, pytest 같은 smoke) production 배포
local에서 adk web 시작하고 chat smoke를 실행하는 개발 검증 운영 인증/배포 UI
runtime wiring/configuration을 TODO 경계로 남긴 source bundle private endpoint/credential/실제 비즈니스 로직 포함

scaffold-plan validation 규칙

  • source는 반드시 approved_workbench_artifact여야 한다.
  • approved 후보만 포함된다.
  • raw requirement는 직접 코드 생성 입력이 될 수 없다.
  • af-run-manifest.json이 있으면 analysis_reviewed, boundaries_approved, runtime_contracts_approved가 모두 true여야 하고 design stage가 complete여야 한다.
  • catalog-bound 항목(Agent/Workflow/Adapter/Remote A2A)은 runtime contract로 해석하되, 실제 runtime wiring은 reviewed TODO boundary로 남긴다.
  • runtime_mock이 있으면 generated source의 deterministic stub output으로 포함될 수 있다 (test double, synthetic 데이터만).
  • 필수 runtime_contracts가 approved가 아니거나 needs_info 정책을 남기면 source generation blocker.
  • 모든 scaffold module은 승인된 ModuleCandidate에서 와야 하며 Graph IR node로 덮여야 한다.
  • runnable business logic은 out of scope.
!

scaffoldPlan.validation.can_generate_source가 false거나 Graph IR에 errors가 있으면 ADK Runtime Handoff 화면 상단에 empty-state 패널이 뜨고 모듈 검토로 이동 버튼이 나온다. 다시 6장 흐름으로 돌아간다.

CLI source generation gate

scripts/generate-adk-source.mjs는 UI에서 만든 계획을 그대로 믿지 않고 artifact를 다시 대조한다.

검사차단되는 경우

generated agent.py의 skeleton edge도 scaffold-plan.modules 배열 순서가 아니라 검토된 Graph IR edge를 따라 만든다.

Stub runtime 배너

다음 중 하나라도 해당하면 임베드 패널 상단에 노란 배너가 표시된다.

  • runtimeMode === "stub"
  • chat-smoke 응답 event에 "stubbed_runtime_contract" 표식이 있음
  • Catalog mock-ready 항목의 runtime_mock 출력
!

배너 문구: “스텁 런타임 — graph 구조만 검증합니다. 실제 모델/어댑터 호출은 발생하지 않습니다.”

이 배너는 stub 출력과 실제 비즈니스 로직을 절대 혼동하지 못하게 만든다. 절대 제거하지 않는다.

“Done”의 의미

Agent Factory 작업은 다음을 모두 만족할 때만 done이다.

  • raw requirement가 scaffold input으로 쓰이지 않는다.
  • module 분류가 활성 taxonomy를 따른다.
  • category에 맞는 subtype 필드가 존재한다.
  • Remote A2A는 high-friction이고 contract-backed다.
  • Runtime 계약과 manifest 승인 상태가 source generation 전에 맞춰져 있다.
  • schema, validator, analyzer types, UI label이 enum 변화에 맞춰 정렬되어 있다.
  • review artifact와 deferred fixture가 검증을 통과한다.
  • UI 시각 변경이 있으면 screenshot으로 확인되었다.
  • private banking 데이터/credential/endpoint/deployment script/organization-specific runtime 코드가 추가되지 않았다.

퀴즈

Q1. 후보 2개가 needs_info인 상태에서 export로 가서 ADK Runtime Handoff를 눌렀다. 어떻게 될까?

정답: 차단. candidate-level missing은 hard gate다. 모듈 검토에서 Resolution Draft → 반영 적용 → 승인을 거쳐야 한다.

Q2. chat-smoke 응답에 "stubbed_runtime_contract" 표식이 있다. UI에는 무엇이 나타나야 할까?

정답: 노란 stub 배너. stub 출력과 실제 비즈니스 로직을 절대 혼동하지 못하게 만드는 안전장치다. 절대 제거하지 않는다.

Q3. saved record를 다시 열었더니 scaffoldReady === true다. 어디로 landing할까?

정답: export. scaffoldReady가 true면 바로 ADK Runtime Handoff 화면으로 들어간다.
