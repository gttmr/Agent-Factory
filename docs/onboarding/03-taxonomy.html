3. Taxonomy 결정

DesignWorkbench의 모듈 검토 패널에서 한 후보의 분류를 정하는 단계다. taxonomy를 마음대로 늘리지 않는 것이 분석 일관성을 유지하는 핵심이다. 이 장은 top-level module_category와 그에 딸린 subtype을 어떻게 고르는지 결정표와 분류기 위젯으로 설명한다.

module_category — 네 개 뿐이다

값한 줄 정의대표 신호
◆ agent 판단/요약/분류/추천/triage 같은 reasoning 책임 “판단”, “요약”, “등급”, “추천 사유 작성”, “비교 후 의견”
▶ workflow 여러 Agent/Adapter/Workflow를 조율하는 control flow “순서”, “병렬”, “fan-out/fan-in”, “loop”, “human 승인”, “route”
⚙ adapter 호출 가능한 capability (MCP tool, API, retrieval, rule, 외부 서비스 등) “API 호출”, “OCR”, “정책 검색”, “규정 조회”, “데이터 조회”
⇨ remote_a2a 독립 owner를 가진 원격 에이전트와의 프로토콜 경계 “다른 팀이 운영하는 에이전트”, “Agent Card 있음”, “A2A 프로토콜로 호출”
!

모호하면 새 카테고리를 만들지 말고 evidence.assumptions나 missing_information에 남긴다. 분석 화면에서 후보를 needs_info로 두는 것이 가짜 분류보다 항상 낫다.

Runtime 계약도 top-level category가 아니다. MCP, EAI/Legacy, Context Manager, Callback Broker, ADK callback, async resume는 후보의 책임 분류를 유지한 채 runtimeContracts에서 별도 승인 artifact로 검토한다.

분류기 — 신호 체크해보기

아래 위젯에서 요구사항이 보이는 신호를 체크하면, 워크벤치가 어떤 module_category를 제안할지 보여준다. 실제 워크벤치의 분류기가 아니며 학습 보조용이다.

이 후보의 요구사항에서 보이는 신호를 모두 체크해보세요.
i

여러 카테고리 신호가 함께 보이면 일반적으로 후보가 둘 이상일 가능성이 높다. 예: “OCR(adapter) → 정책 검색(adapter) → 판단(agent)”은 세 개의 후보로 분리하고, 이들을 묶는 흐름이 명시적이면 별도 workflow 후보를 추가한다.

실전 미니 퀴즈

Q1. “여신 정책 문서를 벡터 검색으로 가져온다.”

정답: adapter / retrieval — 검색은 callable capability이고, 벡터/문서 검색이므로 adapter_kind: retrieval이 가장 가깝다. rule_registry는 “관리되는 정책 룰 lookup”일 때 쓴다.

Q2. “OCR과 정책 검색을 동시에 호출하고 둘 다 끝나면 판단 에이전트를 실행한다. 판단 결과가 보완 요청이면 사람 검토로 보낸다.”

정답: workflow / graph — fan-out/fan-in과 명시적 human input 라우팅이 분명하므로 graph workflow다. orchestration은 graph topology가 아직 모호할 때다.

Q3. “코어뱅킹 계좌 잔액 API(EAI 경유)를 호출해서 잔액을 가져온다.”

정답: adapter / legacy_api — EAI/Legacy 시스템 호출은 legacy_api다. 추가로 MCP/EAI/Legacy adapter contract를 Runtime 계약에서 검토한다(7장).

Q4. catalog에 등록된 공통 Workflow가 runtime_binding: remote_a2a로 호출되고 있다. 이 후보의 module_category는?

정답: workflow. runtime_binding은 “어떻게 호출되는가”이지 “책임 종류”가 아니다. 독립 원격 에이전트 계약 자체를 새로 설계한다는 증거가 없으면 카테고리는 workflow를 유지한다.
