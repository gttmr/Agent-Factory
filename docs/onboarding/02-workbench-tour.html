2. 워크벤치 한 바퀴

⚠️ Stale (PR6 이전 wizard UI 기준) — 이 챕터는 PR1~PR6 마이그레이션 전의 단일 페이지 wizard surface(intake → analysis → modules → graph → contracts → catalog → saved → export)를 묘사한다. 현재 워크벤치는 router-driven 5-route 모델(/ Landing → /af/:reqId/{analyze,design,build,verify} → /catalog Reuse Hub)이다. 본문 재작성과 새 스크린샷은 docs/workbench/follow-ups/07-onboarding-html-refresh.md 브리프에서 다룬다. 현재 UI 사실관계는 docs/workbench/agent-factory-harness.md의 “Workbench surface” 절을 참고한다.

Agent Factory 워크벤치는 단일 페이지 wizard다. 좌측 rail에는 항상 보이는 단계와 산출물 상태에 따라 열리는 조건부 단계가 있다. 각 단계는 “무엇을 결정하는 화면인지”가 분명히 다르다. 이 장은 각 단계가 어떤 입력을 받고 어떤 산출물을 만드는지 한 번에 본다.

워크벤치 단계 한눈에

intake → analysis → modules → graph → [runtimeContracts] → [a2aContracts] → catalog → saved → export ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓ 입력 이해 확인 판단/승인 흐름검증 Runtime 계약 Remote A2A 재사용 저장 ADK 소스 생성

좌측 rail은 의미 단위로 4개 그룹이다:

  • 입력 — intake, analysis
  • 검토 — modules, graph, runtimeContracts, a2aContracts
  • 자산화 — catalog, saved
  • 생성 — export (ADK Runtime Handoff)

runtimeContracts는 Runtime 계약 후보나 catalog-bound 후보가 있을 때 열리고, a2aContracts는 Remote A2A 후보나 A2A 계약이 있을 때 열린다. 조건이 없으면 rail에 나타나지 않는다.

각 단계의 책임

1

intake — 요구사항 입력

raw requirement 텍스트와 requester context를 넣는다. 워크벤치는 여기서 코드를 만들지 않는다. 오른쪽 파일 입력 패널에서는 analysis-result.json과 af-run-manifest.json을 browser file import로 불러올 수 있다.

2

analysis — 이해 확인

Codex CLI가 raw requirement를 정규화한다. 화면 상단의 핵심 계약 5개(목표, 도메인, 입력, 출력, 시스템)가 맞는지 본다. 가정/누락 정보/모순/위험 신호는 보조 drawer에 둔다. 이 화면은 보고서가 아니라 “모듈 검토로 넘어가도 되는가”를 보는 게이트다.

3

modules — Module Review Board

각 ModuleCandidate를 approved/deferred/rejected/needs_info로 판단한다. 신규 모듈과 카탈로그 계약 두 탭으로 나뉜다. needs_info는 “해결 초안 생성” → Resolution Draft 검토 → 반영 적용 → 승인 순서로 푼다 (6장).

4

graph — Process Flow 검증

승인된 모듈로 Graph IR을 본다. 고립된 node, 누락된 join, route_condition이 없는 route edge 같은 구조 오류를 잡는다. Module Review에서 저장하면 deterministic하게 재생성된다.

5

runtimeContracts — Runtime 계약 검토

MCP, EAI/Legacy Adapter, Context Manager, Callback Broker, ADK callback, async resume 계약을 검토한다. 필수 계약은 contract_status: approved가 되기 전까지 scaffold/source generation blocker다.

6

a2aContracts — Remote A2A 계약 검토

remote_a2a 후보가 있으면 Agent Card, 인터페이스, message/task/artifact 계약, auth, timeout, retry, fallback, audit, data policy를 검토한다. 없으면 rail에서 숨겨진다.

7

catalog — 재사용 결정

기존 catalog의 agent/workflow/adapter/remote_a2a 계약 중 어떤 것을 재사용할지, 어떤 후보를 새로 등록할지 정한다. 이 단계가 “신규 vs 재사용”을 가르는 곳이다.

8

saved — 저장된 분석

현재 분석을 SavedAnalysisRecord로 저장하거나 이전 record를 불러온다. 여기서 현재 검토 상태의 analysis-result.json과 연결된 af-run-manifest.json을 내보낼 수 있다.

9

export — ADK Runtime Handoff

승인된 산출물로 scaffold-plan.json을 만들고 ADK source bundle을 생성한다. Manifest 승인, Runtime 계약 승인, Graph IR coverage가 맞지 않으면 source generation이 차단된다 (8장).

색·글리프 한 줄

워크벤치는 카테고리를 항상 색과 글리프로 즉시 구분한다. 가이드 안에서도 같은 매핑을 쓴다.

카테고리색글리프의미
◆ agent보라◆reasoning 책임
▶ workflow주황▶control flow / orchestration
⚙ adapter청록⚙callable capability
⇨ remote_a2a빨강⇨원격 protocol boundary

빨강은 Remote A2A 외에는 쓰지 않는다. 위험 신호(risk_signals)는 별도 핑크 배경 체계이며 자동 반려 조건이 아니다.

처음 실행해보는 추천 순서

  1. cd packages/web && npm install && npm run dev -- --host 0.0.0.0 --port 5173 --strictPort 후 http://127.0.0.1:5173/에서 워크벤치를 연다.
  2. intake 단계에서 예시 불러오기를 누른다.
  3. 요구사항 분석으로 analysis를 본다 — 핵심 계약 5개가 맞는지 확인한다.
  4. modules 단계에서 후보 목록을 본다. needs_info가 있으면 6장 절차를 따른다.
  5. graph 단계에서 fan-out/join/loop/human input이 보이는지 확인한다.
  6. Runtime 계약과 Remote A2A 계약 단계가 나타나면 모두 승인 상태인지 확인한다.
  7. 모두 approved면 export에서 ADK Runtime Handoff와 smoke macro를 실행한다.
i

매뉴얼 브라우저 테스트는 고정 포트 5173에서만 한다. 다른 포트로 fallback되면 안 된다. 자세한 정책은 CLAUDE.md의 dev server reachability 절을 참고.
