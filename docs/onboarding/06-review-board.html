6. Design Review

Design route는 분석 결과를 승인 가능한 설계 artifact로 바꾸는 결정 표면이다. 상단 Design Skill Runner는 patch를 제안하고, 아래 모듈/Graph IR/Runtime 계약/Comments 패널에서 개발 리더가 최종 검토한다. 이 장은 status 4개의 의미, Resolution Draft 적용, 2계층 missing-information 게이트를 본다.

두 작업면

탭다루는 것편집 범위
신규 모듈 catalog_entry_id가 없는 후보 분류, subtype, 입력/출력 계약 수정 가능
카탈로그 계약 catalog_entry_id가 있는 후보 (기존 runtime contract) 카탈로그 원본은 read-only. 현재 분석의 입력/출력 override와 Graph 연결만 편집.
i

카탈로그 원본 contract, registry, MCP/A2A binding은 Design review에서 바꾸지 않는다. Reuse Hub의 root별 pin 또는 catalog-delta 제안으로 별도 처리한다.

status — 4개만 허용

값의미downstream 영향
approvedGraph/Catalog Review의 기준 후보로 포함Graph IR에 포함, scaffold-plan에 들어감
deferred판단은 유효하지만 이번 범위에서 보류이번 scaffold-plan에서 제외
rejected후보로 사용 안 함regenerated Graph IR에서 제외
needs_info승인 전 추가 정보 필요scaffold-plan의 hard blocker
!

approved로 올리려면 missing_information이 비어 있어야 하고, 정보 필요 상태였던 후보는 Resolution Draft가 적용되어 object schema와 smoke 계약이 검토된 상태여야 한다. Source generator는 scaffold-plan의 module id가 승인된 ModuleCandidate에서 온 것인지 다시 확인한다.

Resolution Draft 적용 (needs_info 후보 풀기)

1

Design Skill Runner 실행

analysis_reviewed=true 상태에서 Design Skill Runner를 실행한다. Runner는 누락 항목 답변, object schema 보강, patch preview, smoke_spec 후보를 proposed artifact로 만든다.

2

diff/preview 검토

누락 항목 답변과 근거, 입력/출력 object schema의 구조, 현재 분석 artifact에 반영될 patch preview, structural/runtime smoke에 사용할 smoke_spec을 같은 run detail에서 본다.

3

제안 적용

OK라면 제안 적용을 누른다. 그 순간 워크벤치는:

  • missing_information → resolved_missing_information으로 이동
  • missing_information은 비움
  • resolution_applied_at 기록
  • schema_review_state: applied
  • smoke_spec 저장
4

검토 승인

그 다음 status select나 gate 패널에서 사람이 승인한다. Stage Runner 성공만으로 boundaries_approved 또는 runtime_contracts_approved가 자동으로 켜지지 않는다.

×

Resolution Draft는 LLM이 만든 검토 초안이지 승인 근거가 아니다. 자동 적용되지 않으며, 검토를 거치지 않은 proposed artifact가 scaffold-plan으로 흘러가지 못하게 막는 것이 이 단계의 목적이다.

2계층 Missing-information 게이트

계층위치성격차단 대상
Requirement-level evidence.missing_information SOFT Reviewer attestation. AnalysisResult 행마다 “수용” 토글이 있고 acceptedMissing 배열로 기록된다. 차단하지 않음. scaffold-plan 생성 가능. Saved record와 ADK Runtime Handoff 헤더에 “요구사항 누락 수용 N건” chip으로 보존된다.
Candidate-level ModuleCandidate.missing_information, unresolved status === "needs_info" HARD 승인 차단. scaffold-plan blocker. 미해결 후보는 approved로 전환 불가.
i

scaffold-plan을 만들 때 미해결 후보가 있으면 다음 한국어 blocker가 emit된다:

정보 필요 후보 N개를 모듈 검토에서 Resolution Draft를 반영하고 승인하세요.

warning에도 “정보 필요 후보 N개 — 모듈 검토에서 Resolution Draft 반영 필요”가 누적된다.

Skill-led DLC, Stage Runner, browser import로 들어온 artifact도 같은 규칙을 따른다. module-candidates.json 또는 analysis-result.json에서 승인되지 않은 후보가 scaffold-plan.json에 들어 있으면 CLI generation 단계에서 다시 차단된다.

risk_signals — 자동 반려가 아니다

위험 신호는 analyzer evidence이며 사람 검토/감사/데이터 정책을 드러내기 위한 정보다. 자동 차단 조건이 아니다.

personal_data financial_data credit_decision_support customer_impact external_message transaction_write human_approval_required audit_required

검토 질문 체크리스트

이 후보의 책임 종류는?

reasoning owner(agent) / control flow(workflow) / callable capability(adapter) / Remote A2A 계약(remote_a2a) 중 무엇인가?

subtype이 category와 맞는가?

agent는 agent_kind, workflow는 workflow_kind, adapter는 adapter_kind, remote_a2a는 remote_contract_kind. 잘못된 subtype은 schema validator가 잡는다.

Process Flow에서 실행 순서/boundary가 설명되는가?

module-bound node에 incoming/outgoing edge가 모두 있는가? 사람 승인이면 human_input이 graph에 들어가 있는가?

object 입력/출력은 Schema Tree로 검토했는가?

object/array<object>는 textarea가 아니라 펼침 가능한 Schema Tree로 본다. 하위 필드 타입 pill까지 확인.

smoke_spec이 synthetic input / sample message / expected output shape를 갖는가?

후속 runtime smoke 입력이 된다. 현재 워크벤치 UI 안에는 chat-smoke runner가 없으므로 별도 터미널 검증에서 소비한다.

Adapter로 충분한데 Remote A2A로 과분류하지 않았는가?

MCP/EAI tool, retrieval, external service는 일단 adapter로 본다. remote_a2a는 독립 원격 에이전트 계약 증거가 있을 때만.

ADK component hint가 category로 잘못 승격되지 않았는가?

예: “LoopAgent”라는 단어가 보인다고 그것이 별도 workflow_kind가 되는 것이 아니다. Graph IR loop_region으로 들어간다.

approved로 올리기 전 owner/auth/audit/data policy 정보가 있는가?

특히 remote_a2a와 위험 신호가 있는 후보는 이 정보 없이 승인하지 않는다.

퀴즈

Q1. 후보 A가 needs_info다. Design Skill Runner가 좋은 보완 답변을 proposed artifact로 만들었다. 다음으로 해야 할 일은?

정답: Resolution Draft를 검토하고 제안 적용한 다음 승인한다. proposed artifact는 자동 적용되지 않는다.

Q2. evidence.missing_information(요구사항 수준)에 항목 3개가 남아 있다. 모두 “수용” 토글했다. 이게 scaffold-plan 생성을 막을까?

정답: 아니오 (soft). 요구사항 수준 missing은 reviewer attestation일 뿐이고 scaffold 생성을 막지 않는다. 후보 수준 missing이 hard gate다.

Q3. 후보 B의 risk_signals에 personal_data와 customer_impact가 있다. 자동으로 reject 되나?

정답: risk_signals는 자동 차단이 아니다. 다만 customer_impact는 기본 정책상 “draft_or_recommendation_only”이므로 거래 쓰기 같은 자동 처리는 별도로 검토해야 한다.

Q4. 카탈로그 계약 탭에서 어떤 후보의 catalog 원본 contract를 그대로 바꾸고 싶다. Design review에서 직접 편집해도 될까?

정답: 아니오. 카탈로그 원본은 잠긴 상태로 두고 Reuse Hub의 root별 pin 또는 catalog-delta 제안으로 별도 변경한다. 그래야 다른 분석에 영향이 가지 않는다.
