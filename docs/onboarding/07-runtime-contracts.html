7. Runtime 계약

⚠️ Surface 단어 stale — “워크벤치 wizard의 Runtime 계약 스텝/rail”은 PR6 마이그레이션 전 surface다. 현재 워크벤치는 5-route 모델이며 Runtime 계약 검토 화면은 아직 별도 surface로 부활하지 않았다. 잠정적으로 runtime_contracts_approved는 manifest direct PATCH로만 토글 가능하고, DesignWorkbench는 계약 목록을 read-only로 노출한다. 전용 surface 추가는 docs/workbench/follow-ups/03-runtime-contract-review-surface.md 브리프에서 다룬다. 본문 단어 일괄 갱신은 docs/workbench/follow-ups/07-onboarding-html-refresh.md 브리프에서 다룬다.

MCP, EAI/Legacy adapter, Context Manager, Callback Broker, ADK callback, async resume처럼 “callback과 runtime support 경계”에 해당하는 항목은 top-level module_category를 새로 만들지 않고 AnalysisResult.runtimeContracts에서 별도로 검토한다. 이 장은 이 계약들이 무엇이고, 워크벤치에서 어떻게 다루는지 본다.

왜 별도 artifact인가?

이 경계들은 한 후보의 “분류” 문제가 아니라 “호출 방식·재개 방식·상태 관리 방식”의 문제다. 그래서 module_category를 새로 만들지 않고, runtimeContracts라는 별도 review artifact에 묶었다. 이렇게 하면 taxonomy를 부풀리지 않으면서도 검토 흔적이 남는다.

!

필수 Runtime 계약은 contract_status: approved가 되기 전까지 scaffold-plan의 blocker로 남는다. 실제 endpoint, credential, private customer payload, deployment script는 이 artifact에 절대 넣지 않는다.

다루는 계약 종류

1. MCP / EAI / Legacy Adapter Contract

외부 시스템 호출의 입출력 schema, 성공/실패 예시, mock response를 정의한다. 본문은 catalog/contracts/mcp/*.json에 둔다.

inputSchema호출 입력 JSON schema
outputSchema응답 JSON schema
success_examples성공 예시들 (synthetic만 허용)
error_examples실패 예시들
mock_response.structuredContentdeterministic mock 응답 (local smoke용)

2. Context Manager Contract

여러 호출에 걸친 상태(session/temp/user/app)의 소유권, lifecycle, scope 분리 규칙을 정의한다.

  • state scope: session / temp / user / app 중 무엇을 쓰는가?
  • state key 명명 규칙은?
  • state 만료/삭제 시점은?

3. Callback Broker Contract

비동기 callback 결과를 받아 다시 에이전트 흐름으로 라우팅하는 책임의 계약. 결과 도착 시 어떤 노드/세션으로 reattach할지, dedupe와 순서 보장은 어떻게 할지 정의한다.

4. ADK Callback Responsibilities

ADK가 노출하는 before/after model, before/after tool, before/after agent 같은 callback에서 무엇을 검사·차단·기록할지의 계약. guardrail, audit log 작성도 여기서 정의한다.

5. Async Resume Contract

긴 처리(예: 야간 배치, 외부 시스템 응답 대기) 후 흐름을 재개하는 계약. resume token, idempotency, expiry, fallback을 정의한다.

검토 화면 — 워크벤치의 “Runtime 계약” 단계

워크벤치 wizard의 Runtime 계약 스텝이 이 artifact를 보여준다. Runtime 계약 후보가 있거나 catalog-bound 후보가 있을 때만 rail에 나타난다. 이 화면이 Remote A2A 검토와 Catalog Review 앞에 있는 이유는, 요구사항이 callback/legacy/async resume을 포함한다면 그 경계가 확정된 다음에야 scaffold-plan을 만들 수 있기 때문이다.

i

각 계약은 contract_status를 갖는다. 필수 계약이 approved가 아니면 scaffold-plan validation과 CLI source generation 모두 blocker로 남긴다. 선택 계약이면 warning으로 남길 수 있다.

import/backfill 규칙

analysis-result.json을 browser import할 때 Runtime 계약은 안전하게 정규화된다. 오래된 artifact에 runtimeContracts 필드가 없으면 catalog 기본 계약을 보강할 수 있지만, 명시적으로 runtimeContracts: []가 있으면 reviewer가 비워 둔 상태로 존중한다.

  • malformed contract는 UI가 깨지지 않도록 기본 operation/policy/support 필드를 채운다.
  • catalog-bound 후보의 기본 계약은 Runtime 계약 화면에서 기본값 생성으로 다시 채울 수 있다.
  • 계약 상태를 바꾸면 연결된 af-run-manifest.json의 runtime_contracts_approved 승인 상태도 현재 계약 목록 기준으로 갱신된다.

!

가장 흔한 실수: “MCP/EAI 호출이니까 별도 카테고리지?” → 아니다. 카테고리는 adapter로 두고, MCP/Legacy contract는 Runtime 계약에서 별도로 검토한다.

Catalog contract registry

catalog/contracts/는 catalog 항목을 mock 목록으로 바꾸지 않고, test double을 만들 수 있는 runtime contract 본문을 보관한다.

MCP/A2A registry data는 synthetic sample만 사용한다. private endpoint, credential, deployment script, 실제 고객/은행 데이터는 절대 들어가지 않는다. 위반 시 validator가 잡고, code review에서도 차단된다.

퀴즈

Q1. “MCP server로 노출된 신용평가 외부 도구를 호출한다.” module_category와 Runtime 계약은?

정답: adapter + MCP contract. MCP tool 호출은 보통 adapter 후보로 잡고, MCP contract(inputSchema/outputSchema/examples/mock)를 Runtime 계약에서 검토한다.

Q2. “신청 후 야간 배치로 심사 결과가 도착하면 다음 단계로 진행한다.” 어떤 Runtime 계약이 필수인가?

정답: Callback Broker + async resume. 비동기 결과를 받아 흐름에 재투입하는 책임이 필수다. resume token, idempotency, expiry, fallback이 정의되어야 한다.

Q3. catalog에 등록된 공통 신용평가 workflow가 runtime_binding: remote_a2a로 호출되고 있다. 이 후보를 remote_a2a로 분류해야 할까?

정답: workflow 유지. runtime_binding은 “어떻게 호출되는가”다. 독립 원격 에이전트 계약 자체를 새로 설계한다는 증거가 없으면 카테고리는 workflow를 유지한다.
