1. ADK 기본 개념

이 장은 워크벤치를 설명하기 전에 ADK / A2A / MCP / EAI / Callback / Graph 같은 용어를 “이게 도대체 어디에 있는 거냐”라는 관점에서 한 번 정리한다. 다음 장부터 화면을 보면서 이 그림을 머릿속에 띄워두면 결정이 빨라진다.

전체 그림

요구사항이 들어오면 워크벤치는 그것을 네 종류의 모듈 후보로 나눈다.

◆ agent ▶ workflow ⚙ adapter ⇨ remote_a2a
┌────────── 사용자 요청 ──────────┐ │ │ │ workflow (▶) │ ← 언제 무엇을 실행할지 조율 │ ┌─────┴───────┐ │ │ ▼ ▼ │ │ agent (◆) adapter (⚙) │ ← 판단 ← 호출 가능 기능 │ │ │ │ │ └─────┬───────┘ │ │ ▼ │ │ remote_a2a (⇨) │ ← 독립 원격 에이전트 │ │ └──────────────────────────────────┘

이 네 가지가 워크벤치의 단일 분류 기준이다. retrieval, rule_registry, tool, MCP 같은 것들은 모두 adapter 아래 subtype으로 들어간다. 별도 top-level이 아니다.

각 모듈의 책임

분류 한 줄 정의 일상 비유 대표 신호
◆ agent 판단/요약/분류/추천 같은 추론 책임. “판사” — 입력을 보고 의견·등급·결정 사유를 만든다. “판단해라”, “요약해라”, “등급을 매겨라”, “triage 해라”
▶ workflow 여러 단계를 어떻게/언제 실행할지 조율. “프로젝트 매니저” — 누가 먼저, 누가 다음, 병렬은 누구. “순서대로”, “병렬로”, “재시도 후”, “승인 후 진행”
⚙ adapter 외부 시스템·데이터·계산을 부를 수 있는 호출 가능 기능. “도구” — DB 조회, OCR, MCP 툴, 정책 검색 같은 callable. “조회하라”, “OCR 결과”, “API 호출”, “정책 검색”
⇨ remote_a2a 독립 owner를 가진 원격 에이전트와의 프로토콜 경계. “다른 회사 직원” — 내가 관리 안 하는 사람, 계약서로 부른다. “다른 팀이 이미 운영하는 에이전트”, “Agent Card 존재”, “A2A 프로토콜”
!

흔한 오해: 여러 단계가 있다고 해서 remote_a2a가 되는 것은 아니다. Local workflow 안에서 처리할 수 있는 다단계는 workflow다. remote_a2a는 독립 소유 + 독립 배포 + 자체 lifecycle이 증거로 나올 때만 사용한다.

ADK (Agent Development Kit)란?

ADK는 Google이 만든 에이전트 구축 프레임워크다. 이 워크벤치의 baseline은 ADK Python 2.0 GA(2026년 5월 19일 기준)이며, 다음을 제공한다.

  • LLM Agent — 추론을 맡는 에이전트.
  • Workflow Agent — 여러 노드/엣지로 흐름을 만든다. ADK 2.0에서는 graph workflow와 dynamic workflow로 표현.
  • Tools — 결정적인 외부 동작을 부른다 (워크벤치에서는 adapter로 분류).
  • State / Artifact / Event — 노드 사이에 데이터를 전달하는 채널. Graph IR의 edge_kind에 대응.

이 가이드에서 ADK 1.x의 SequentialAgent/ParallelAgent/LoopAgent 같은 1세대 workflow agent class는 등장하지 않는다. 대신 그 흐름은 Graph IR 내부의 container와 edge로 표현한다. 자세한 매핑은 4장과 5장에서 다룬다.

A2A (Agent-to-Agent)와 MCP (Model Context Protocol)

약어 한 줄 정의 워크벤치에서의 자리
A2A 에이전트 간 통신 프로토콜. Agent Card, Task lifecycle, message/artifact 계약을 정의한다. module_category: remote_a2a 후보의 계약 검토. 일반 워크플로우 안에서 공통 workflow를 runtime_binding: remote_a2a로 부를 수도 있는데, 이때는 분류는 workflow를 유지한다.
MCP LLM이 외부 도구·데이터에 접근하기 위한 표준 프로토콜. inputSchema/outputSchema로 tool을 정의한다. 대부분의 MCP 도구는 module_category: adapter로 들어간다. 계약 본문은 catalog/contracts/mcp/*.json에서 관리되고, 런타임 계약 검토 화면에서 검토한다.
i

“에이전트가 외부 기능을 호출한다”는 표현이 나오면 먼저 adapter로 분류해보자. 그게 뚜렷한 독립 에이전트가 아니면 보통 adapter가 맞다.

EAI / Legacy Adapter / Callback / Context Manager

은행 도메인에서 흔히 등장하는 단어들이다. 이들은 top-level 분류가 아니라 Runtime 계약으로 검토한다 (7장 참조).

개념 설명 워크벤치 자리
EAI / Legacy Adapter 기존 EAI(Enterprise Application Integration) 버스나 메인프레임 API를 호출하는 어댑터. adapter_kind: legacy_api로 분류하고, MCP/EAI/Legacy adapter 계약은 runtimeContracts에서 별도로 검토.
Context Manager 여러 호출에 걸쳐 세션 상태/사용자 상태를 관리하는 책임. Runtime 계약 — Context Manager contract.
Callback Broker 비동기 콜백 결과를 다시 에이전트 흐름으로 라우팅하는 책임. Runtime 계약 — Callback Broker contract.
ADK Callback ADK가 노출하는 before/after model, before/after tool 같은 콜백 훅. Runtime 계약 — ADK callback responsibilities.
Async Resume 긴 처리 후 재개해야 하는 흐름(예: 야간 배치 결과 후 이어서 통보). Runtime 계약 — async resume contract.

Graph IR — 작은 흐름은 모두 여기로

“순차 실행”, “병렬”, “loop”, “사람 승인”은 더 이상 workflow_kind 값이 아니다. 모두 Graph IR(node/edge/container)로 표현한다.

container: parallel_region ┌────────────┐ ┌────────────┐ │ adapter A │ │ adapter B │ ← fan_out └─────┬──────┘ └─────┬──────┘ │ │ └──────► join ◄────────┘ ← fan_in │ ▼ agent (판단) │ ▼ human_input (승인) ← container: human_review_region │ ▼ route_condition="approved" output

이 그림이 곧 workflow_kind: graph로 분류되는 후보의 내부다. 자세한 노드/엣지 종류는 5장에서 본다.

스스로 점검

Q. 요구사항: “신청서 PDF를 OCR로 읽어서 텍스트로 변환한다.” 이 책임의 분류는?

정답: adapter — OCR은 결정적인 외부 처리이므로 adapter_kind: external_service(혹은 별도 정의된 OCR adapter)로 둔다. 판단이 아니므로 agent가 아니고, 흐름 조율이 아니므로 workflow도 아니다. 독립 원격 에이전트 계약이 따로 명시되지 않았으므로 remote_a2a도 아니다.

Q. 요구사항: “OCR 결과와 정책 검색 결과를 동시에 가져와서 둘 다 모이면 판단 에이전트로 넘긴다.” 이 “동시에 가져와서 모이면” 책임은?

정답: workflow — 누구를 언제 호출하고 어떻게 모을지는 조율 책임이므로 workflow이고, parallel_region + fan_out + join + fan_in이 명시적이므로 workflow_kind: graph가 적합하다.

Q. 요구사항: “고객 조회 → 정책 검색 → 추천 사유 작성 — 이 세 단계를 순서대로 실행한다.” 이 흐름 전체를 remote_a2a로 만들어야 할까?

정답: 아니오. Remote A2A는 독립 소유 + 독립 배포 + 자체 lifecycle + auth/timeout/retry/fallback/audit 계약이 보일 때만 사용한다. 단지 “단계가 여러 개”인 것은 local workflow 후보의 이유이지 remote_a2a의 이유가 아니다.
