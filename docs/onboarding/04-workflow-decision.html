4. Workflow 종류 고르기

후보를 module_category: workflow로 정했다면 다음 결정은 workflow_kind다. ADK 2.0 baseline에서 허용되는 값은 단 4개다: orchestration, graph, dynamic, unknown. 이 장은 그 4개를 어떻게 가르는지 결정 트리와 퀴즈로 익힌다.

한 번에 보는 결정 트리

요구사항이 workflow 후보로 보이는가? ─── (no) ──► workflow가 아닐 수 있다 (3장으로) │ (yes) │ ▼ 코드 로직(Python 조건/loop/recursion/ctx.run_node)이 ─── (yes) ──► dynamic 런타임 경로를 직접 결정해야 하는가? │ (no) ▼ 명시적 node/edge/route/join/loop/human input이 ─── (yes) ──► graph 설계 산출물로 필요한가? │ (no) ▼ 상위 조율 책임은 보이지만 graph topology가 ─── (yes) ──► orchestration 아직 핵심 산출물이 아닌가? │ (no — 증거 부족) ▼ unknown

각 값의 사용 신호와 산출물

workflow_kind사용 신호Graph IR 표현
orchestration 여러 모듈을 묶는 흐름은 보이지만 route key, join, loop control 같은 graph 세부가 아직 부족하다. 구현 handoff에서 추가 설계가 필요하다. 최소한의 관찰 가능 흐름만 그린다. 불명확한 branch/종료 조건은 needs_info로 남긴다.
graph 결정적 route, branch, fan-out/fan-in, join, loop가 보인다. human input이 graph 내부의 일시정지/재개 node로 들어간다. nested workflow가 parent graph의 일부로 동작한다. normal_transition, parallel_region + fan_out + join + fan_in, loop_region + loop_control + loop_back + loop_exit, human_review_region + human_input + route, router + edge_kind: route + route_condition.
dynamic Python 조건문, loop, recursion, async orchestration이 중심. 호출마다 branch 수/실행 순서가 바뀜. static graph로 표현하면 지나치게 복잡함. ctx.run_node 기반 composition, checkpointing, resume이 핵심. dynamic_workflow container를 두고 외부에서 관찰 가능한 input/output, human input, remote boundary, 주요 adapter call만 노출한다. 종료 조건/max iteration/fallback/escalation이 없으면 needs_info.
unknown workflow 후보는 맞는데 어떤 종류인지 결정할 증거가 부족함. flow는 그리되 의도/조건은 needs_info로 명시한다.

버리지 말 것: sequence / parallel / loop / human review는 taxonomy 값이 아니다. workflow_kind는 위 4개뿐이고, 그 작은 흐름은 Graph IR 내부 표현으로 들어간다. 새 workflow_kind를 만들지 않는다.

“orchestration vs graph” 결정용 체크리스트

이 요구사항에서 보이는 신호를 모두 체크하세요.

퀴즈

Q1. “고객 응대 흐름 — 먼저 의도를 파악하고, 필요한 adapter를 호출하고, 결과를 정리해 사용자에게 답한다.” 라고만 적혀 있고 어떤 조건에 어디로 가는지는 명확하지 않다. workflow_kind는?

정답: orchestration — 조율 책임은 있지만 명시적 route/join이 아직 없다. 불명확한 branch는 needs_info로 남긴다.

Q2. “OCR과 정책 검색을 동시에 호출하고 둘 다 끝나면 판단 에이전트로 보내고, 판단이 보완 요청이면 사람 검토로 라우팅한다.”

정답: graph — fan-out + join + human_input + route가 모두 명시적이다.

Q3. “요청 type에 따라 호출해야 하는 adapter가 5종에서 12종까지 동적으로 바뀌고, 결과 품질에 따라 추가 호출 수가 런타임에 정해진다.”

정답: dynamic — 호출마다 분기 수/실행 순서가 달라지고 static graph로 표현하면 지나치게 복잡하다. 종료 조건과 max iteration을 별도로 정의해야 한다.

Q4. “여러 단계가 있는 워크플로우다”라는 이유만으로 remote_a2a를 만들어야 할까?

정답: 아니오. Local workflow의 복잡도는 Remote A2A의 이유가 되지 않는다. Remote A2A는 owner/agent card/auth/lifecycle/timeout/retry/fallback/audit이 모두 검증될 때만 만든다.
